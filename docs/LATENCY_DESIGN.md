# 完整任务的速度设计

速度优化以完整任务正确完成为前提。步骤上限改为 10，允许读取、恢复、纠正、写入、检查与最终回答完成；每组使用相同上限。上限是终止保护，任务提前完成就停止，不要求用满。

## 参考实现

| 项目 | 实现方式 | 当前采用的思路 |
|---|---|---|
| [Context Mode](https://github.com/mksglu/context-mode#tools) | 沙盒保留原始输出，只返回必要内容；支持批量执行与多查询搜索，声明 intent 时筛选相关片段 | 在实际工具结果进入模型视图前提取已声明的短字段，减少额外取证请求 |
| [Deep Agents](https://docs.langchain.com/oss/python/deepagents/context-engineering) | 大工具输入和结果外置为文件引用，按需重读或检索；接近上下文上限时才做模型摘要 | 保留完整原文与恢复入口，对小字段直接保留，避免每一步另调模型压缩 |
| [Mem0](https://github.com/mem0ai/mem0#basic-usage) | 接入示例先检索相关记忆，再将短记忆放入生成请求；记忆维护有单独的模型与嵌入成本 | 对明确证据需求在宿主侧先选择原文，而不是让生成模型先决定再取回 |

这些是可借鉴的结构，不构成当前插件准确率或速度的证据。不同模型、工具和任务下的项目自报成绩不能直接迁移。本轮实现不引入摘要模型、向量服务或额外网络检索；实际效果由同轮对照测量。

## 原文字段直送

开启 `eager_evidence=True` 后，FreshWriteGuard 从本轮实际读取结果按宿主已声明的 selector 选择字段。外置入口附上 requested_evidence，包含原值、真实字段位置、来源 ID、读取参数与原文指纹。格式化结果仍由模型提交，宿主核验后才允许写入。

例如现在读取的数组中 event 为 scan_c-901 的 status_code 是 206，发送视图附上整数 206 和实际位置，而不是提前填入答案 206.00。当前读取含同名重复事件时标记 ambiguous，完整来源没有匹配时标记 missing；判断来自实际数据，不是评分标签。未知格式、字段缺失或响应过大时保留正常恢复路径。

投影只来自本轮成功的 handler 返回，历史回显不能产生新证据。完整结果保存在规范消息与 SQLite 中。来源第一次发送后其视图固定，保持任务内前缀稳定；后续读取得到新的来源，不改写已发送的旧视图。

## 少往返与少传输

一次额外的模型恢复请求包含网络等待、输入处理和生成时间。明确需求的字段直送减少这一次请求；对于日志末尾目标，也能避免先错查 JSON、再连续分页。宿主选择本地字段，不增加模型调用。

保持历史前缀与工具 schema 稳定，有助于利用服务商缓存。缓存命中 token 仍计入输入，命中率与费用以返回 usage 为准。不能从少 token 或缓存命中推断一定更快，生成长度和服务商排队也影响时间。

批量处理只适用于没有先后依赖的读取。写入与检查按顺序执行，不为了速度跳过检查或把检查放在写入之前。当前首版没有自动并行执行任意业务工具。

## 测量与验收

当前配置使用 12 个冻结的合成模板，各重复 3 次；三组随机交错执行。重复运行用于观察生成与网络波动，仍只有 12 个任务模板，不记作 36 个独立任务。

三组为 Full + 相同核验、增加步骤的原插件、增加步骤并直送字段的插件。所有组采用相同工具、写入规则、执行要求与 10 步上限；因此增加步骤的效果与直送字段的效果可以分开比较。

先核对全部答案、文件状态、实际操作与最终回答，再比较整任务平均数、中位数和 P95、请求数与完整成本。预先设置 P95 相对 Full 不超过 1.15 为本轮速度目标，同时希望达到低于 Full 的耗时。任何失败和补做都保留，不能重复运行到通过后只报告成功的一次。

完整任务时间包含准备请求、模型 API 与本地工具执行；评测日志写入开销按既有口径排除。摘要、向量和建索引成本如后续引入，也应单独记录并纳入相应任务成本。
