# 和老师讨论项目

## 可以这样介绍当前成果

我读了 GPTCache 和 LLMLingua，尝试把问题拆成两部分：重复请求是否需要再调用模型，以及未命中的请求能否减少上下文。
我搭了一个可复现的教学基线：用 BM25 选择相关句子，再比较精确缓存和词面近似缓存。
初版由 AI 辅助搭建，我会逐段理解代码，并自行补充数据、真实模型实验和算法改进。
当前有 34 条人工样例和 20 种离线配置，发现降低近似匹配阈值虽然提高命中率，但会把询问不同事实的问题混淆。
DeepSeek 实验入口已实现并通过模拟接口测试；真实 API 结果仍待运行，不能把当前字符节省率写成 token 节省率。

## 适合继续研究的问题

“在问答质量下降不超过预先设定范围时，压缩预算和缓存阈值怎样共同选择？”

这是一个实验问题，不预先声称创新性。组合缓存与压缩本身不是新颖性证明。
一个可落地的小改动是：识别数字、否定、条件约束等高风险差异，限制近似缓存复用；或在压缩时保留相邻证据。

## 后续实验设计

- 准备至少数百条问题作为下一阶段目标，覆盖多份文档；当前 34 条仅用于检查代码和学习。
- 按文档划分开发/验证/测试集，在验证集选阈值；测试集固定后不再为了好看调参数。
- 固定模型 ID、提示词、数据版本和运行设置。记录 API 实际返回的模型名。
- 比较完整输入、头部截断、BM25、LLMLingua-2；另比较无缓存、精确缓存、embedding 语义缓存。保持预算可比。
- 分别报告冷启动、已有缓存和不同重复请求比例，避免只靠大量人为重复得到高节省率。
- 核算压缩、embedding、检索、生成全过程的耗时与费用。记录输入、输出、服务端缓存 token；单价按实验当天平台为准。
- 质量采用任务匹配的 EM/F1 或人工评分，不能只使用字符串包含率。复杂判断报告人工标注规范及分歧处理。
- 多次运行并给出变动范围。延迟需控制服务端缓存、网络波动和策略执行顺序。
- 保存失败样例，尤其是实体变换、数字、否定、时效、跨句推理、无答案问题。

## 不宜写进简历或汇报的说法

- “实现了 GPTCache 和 LLMLingua 的完整复现”：当前没有。
- “DeepSeek token 消耗下降 51.2%”：当前这个数字是离线字符统计。
- “正确率 97.1%”：需要说明这是哪份数据、哪个回答器、什么指标。
- “提出了全新算法”：需要先查相关工作和完成对照实验。

更准确的项目描述：

“构建面向文档问答的上下文筛选与回答缓存实验框架，实现 BM25 句子选择、缓存隔离与消融评测；提供 DeepSeek usage 采集接口，并分析近似缓存错误复用现象。”
