# 跟着一次请求读代码

## 1. 先理解输入

每条数据包含 `query`（问题）和 `context`（材料）。
`evidence` 和 `expected` 是评测标注，只在运行完成后计算指标，算法看不到它们。
`fact_id` 标记两个问题是否询问同一事实，也只用于评测错误缓存复用。

从 `data/toy_qa.jsonl` 第一条开始，问题是图书馆周日是否开放。

## 2. `Pipeline.run` 先找缓存

缓存的范围由原始材料、用户范围、模型、提示词和压缩配置的哈希确定。
例如同样问“周日开放吗”，如果材料从“不开放”变成“开放”，哈希改变，不能再复用旧回答。

`exact` 要求问题字符串完全相同；保留大小写与标点差异。
`lexical` 则把中文字符/双字片段、英文词的出现次数构成向量，再计算余弦相似度。
它不理解语义，所以相似问题中的不同配额类别可能被混淆。
目前按列表扫描，小数据易读，大数据时速度和内存都需要改进。

## 3. 未命中时才压缩

`compress` 将材料拆成句子，并用 `bm25_scores(query, sentences)` 算相关性。
常出现的词区分能力低，少见而匹配问题的词作用更大；得分还考虑词频饱和和句子长度。

随后从得分高的句子开始尝试放入预算。每次重新统计拼接后的长度，确保换行符也计入预算。
最后按原文顺序输出，避免仅因排序就改变段落顺序。
它不会强行切掉半句话；预算过小时可能一整句也放不下，返回空上下文。
系统指令和问题不被压缩，因此“上下文保留一半”不等于“整个输入减少一半”。

当前是贪心选择，不保证在给定预算内取得全局最优证据组合。分句规则也无法完整处理缩写、表格或代码。

## 4. 用回答器生成结果

离线 `extractive_answer` 再找最相关的一句话，只供演示。多句推理题会暴露它的能力限制。
DeepSeek 版本通过 `answer_fn` 替换为真实接口：发送压缩后上下文，收集真实 usage 和回答。
只读取环境变量中的密钥，不会把密钥写进结果。

## 5. 评分与统计

- 输入减少：按整个请求流累计，缓存命中为零调用。
- 全部证据保留：当前问题标注的每句证据是否仍在保留上下文里。
- 答案包含：回答是否含标准答案片段；只是粗指标，会被否定、冗余或巧合干扰。
- 错误复用：缓存来源和当前问题的事实标签是否不同。

这一现象说明：缓存来源的上下文仍含正确证据，并不代表缓存答案回答了新问题。
所以在较宽松近似匹配阈值下，证据保留率可能很高，而答案正确性仍下降。

## 6. 你可以亲手改的地方

先尝试把 `--ratios` 从 `0.25 0.5 0.75` 改成 `0.1 0.3 0.6`，观察预算效果。
再把 `--thresholds` 改成 `0.6 0.8 0.95`，观察近似缓存错误。
然后添加自己写的反例，如“至少 10 小时”和“至多 10 小时”。不要只增加容易得到正确答案的样例。

下一步算法练习：选中句子后尝试保留前后各一句，仍严格检查预算，评估是否改善跨句证据。
这个改动有可能占用预算、挤掉更重要的句子；实验要允许得到负结果。
