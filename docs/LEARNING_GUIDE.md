# 从 Python 脚本到 token 节省实验

你的起点是“能写 Python，了解一点机器学习”。先掌握缓存、检索和评测，不必先训练模型，也不必先读完 Transformer 推导。

## 先分清五件事

1. **token**：模型分词器处理的单位，不等于汉字或英文单词。同一段话换模型可能得到不同 token 数。
2. **输入压缩**：把材料缩短，再发送给模型。风险是把答案依据也删掉。
3. **回答缓存**：已有可复用答案时直接返回，避免再次生成。风险是误复用、过期或跨用户串用。
4. **服务端前缀缓存**：复用一段重复输入的计算。通常不会让逻辑上的输入文本消失；账单要按平台规则核算。
5. **推理效率**：包括时间、显存和计算量；节省 token、节省费用和加速不是完全相同的指标。

你可以把“减少输入”“避免调用”“减少生成”“复用计算”画成四条路线。
本项目先做前两条，暂不研究大模型内部 KV-cache 算法。

## 阅读推荐（按这个顺序）

### 1. rank_bm25：最容易亲手实现的相关性筛选

[项目与示例](https://github.com/dorianbrown/rank_bm25)

通俗理解：一句话与问题共享关键词越多，越可能有用；少见词通常比常见词更有区分度。
BM25 还会控制词频重复和句子长度的影响。

先看 README 的用法，再读 `BM25Okapi.get_scores`。不必一开始就比较所有 BM25 变体。
本项目使用常见的正值 IDF 形式，与 rank_bm25 默认实现的 IDF 处理不完全一样，不声称数值逐项相同。

练习：写出 5 句话，用“图书馆周日开放吗”排序，把最相关的句子放到材料末尾，比较“取开头”与“按问题筛选”。
完成标准：你能解释为什么排序依赖问题，以及为什么同义词可能排不好。

### 2. Selective Context：哪些内容可以删除

[EMNLP 2023 论文](https://aclanthology.org/2023.emnlp-main.391/)

通俗理解：用模型估计内容的信息量，删除一些冗余部分。它不是本项目使用的关键词排序。
先读摘要、方法总览和实验表，再了解 self-information：某个内容越出乎模型预料，自信息通常越大。

练习：手工压缩一段材料，把“不”“至少”“2026”等词删掉，观察意思是否改变。
完成标准：能说明“高信息量”不一定等于“对当前问题最重要”。

### 3. LongLLMLingua：把问题纳入压缩过程

[ACL 2024 论文](https://aclanthology.org/2024.acl-long.91/) · [代码仓库](https://github.com/microsoft/LLMLingua)

通俗理解：长材料里重要内容的密度和位置都影响模型使用信息；压缩应考虑当前问题。
先看整体流程图，再关注相关性选择、预算分配和内容位置，不用先复现全部实验。

练习：对同一份校园规定分别询问“截止日期”和“材料份数”，观察筛出的上下文如何变化。
完成标准：能解释本项目的 query-aware 句子筛选与论文方法的共同动机，以及算法上的明显差别。

### 4. LLMLingua-2：把保留/删除看成分类任务

[ACL Findings 2024 论文](https://aclanthology.org/2024.findings-acl.57/) · [项目说明](https://github.com/microsoft/LLMLingua)

通俗理解：先利用强模型生成压缩监督，再训练较小的模型决定内容是否保留。
先理解数据蒸馏和 token 分类这两个词，暂时不训练模型。

练习：自己给 10 句话标注“保留哪些词”，找出删词之后含义变化的案例；以后再运行官方预训练模型。
完成标准：能区分“基于模型打分”“基于学习的分类”“本项目的检索基线”。

### 5. Prompt Compression Survey：给知识搭框架

[NAACL 2025 综述](https://aclanthology.org/2025.naacl-long.368/)

通俗理解：hard prompt 通常仍是可读文本，soft prompt 则可以是学习出的向量表示。
先读分类图和结论，把已读论文放进框架，不必逐篇追引文。

练习：用一页纸总结每种方法是否需要训练、是否能用于只开放 API 的模型、是否需要额外压缩成本。

### 6. LongBench：学习怎么公平做评测

[官方数据与评测代码](https://github.com/THUDM/LongBench)

它帮助你从“压缩后看起来还行”转向“在问答等任务上测质量”。仓库同时包括不同版本，使用时明确版本和子任务。
先读原始 LongBench 的数据格式、任务划分和指标，从中英文问答的小子集开始。
先检查许可和下载要求，再保存样本 ID、版本、抽样种子；不要混用不同版本的分数。

练习：固定一批问题，对完整输入和压缩输入使用同一个模型，比较输入 token 和答案质量。
完成标准：能解释为什么长度下降 50% 不代表费用下降 50%，更不代表质量保持不变。

## 两周实践安排（每天约 1–2 小时，可自行放慢）

| 天数 | 任务 | 产出 |
|---|---|---|
| 1–2 | 跑通离线命令，读 `CounterBackend`、`sentences`、`terms` | 能区分检索分词与模型 tokenizer |
| 3–4 | 读 `bm25_scores` 和 `compress`，手工构造 5 句话 | 一张句子得分与保留结果表 |
| 5–6 | 读缓存实现，修改数字、否定和上下文 | 3 个错误近似复用案例 |
| 7 | 看生成报告，比较 25%/50%/75% 保留比例 | 解释一个省得多但质量差的配置 |
| 8–9 | 配置 DeepSeek，先跑 4 条，再扩到 34 条 | 真实 usage 和手工检查的答案 |
| 10–11 | 自己收集/编写更多不同文档，分验证集和测试集 | 独立测试集与数据说明 |
| 12 | 阅读 LongLLMLingua 或 LLMLingua-2 的方法部分 | 1 页读书笔记 |
| 13 | 加一个小改动：相邻证据保留或风险问题禁用近似缓存 | 消融实验：有/无改动的差异 |
| 14 | 整理图表、失败案例与局限 | 向老师汇报的 5 分钟讲稿 |

## 读论文时只先回答这五个问题

1. 它减少的是输入 token、调用次数、输出 token，还是计算开销？
2. 它怎样决定删什么或复用什么？
3. 需要训练、GPU、额外模型或付费调用吗？
4. 用什么任务衡量压缩后仍然答得对？
5. 在哪些情况下会失败，我能否复现一个失败案例？

能清楚回答这五个问题，比只记住“最多压缩多少倍”更有助于与老师讨论。
